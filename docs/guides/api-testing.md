# API testing

A UI test does three things beside the screen: it makes the data it needs, it removes what it made, and it checks
what was stored. Bruinet does these through the service the app itself calls, with an **API session** that holds the
rules every suite needs, and **API objects** a suite writes over it. A test calls API objects, as it calls page
objects: never the session, never an HTTP client.

```text
Tests, scenarios, specs
  API objects (the suite's: Contacts, Projects)        beside page objects
    ApiSession and its guards (Bruinet.Core.Api)         beside controls and contexts
      HttpClient, or a client generated from a description
```

Bouw7's suite is the worked example: `Bouw7.Web.UITests/Support/Api`.

## The API session

```csharp
var options = new ApiSessionOptions
{
    BaseAddress = new Uri("https://api-acc.example.com"),
    AllowedHosts = ["*-acc.example.com"],
};
using var session = new ApiSession(options, TestAccounts.Default.Get("Creator"), signIn);
```

| The session | What it does |
| --- | --- |
| The hosts it may call | `AllowedHosts` (a name, or a pattern with a leading star) is checked before every call. A suite for an acceptance environment names its acceptance hosts, and no test reaches another |
| The account | An `IApiSignIn` signs each call: `SavedSignIn.Token` (the token the web app itself gets, from a browser's saved sign-in; `Bruinet.Html.Playwright`), `ApiSignIns.ClientCredentials`, `ApiKeySignIn`, or a `BearerSignIn` with your own way to fetch a token. A token is fetched again a minute before it runs out, and once when the service answers 401 |
| Writes | An account whose `Writes` is `no` in `TestAccounts.md` sends nothing but GET, HEAD and OPTIONS: the call is refused before it is sent. A search by POST is named in `ReadPaths` |
| Every call | A line in the step log (`api`: method, path, account, status, time), and an `ApiExchange` in `Exchanges`, with the fields of `MaskedFields` (`password`, `token`, …) as `***`. `BRUINET_API_EXCHANGES=<file>` appends every exchange of a run to a file, the page's own calls too |
| A failure | `ApiCallException`, naming method, path, account and status. `Get` gives null for a 404 |
| Clean-up | `Made(resource, id)` registers the delete of what was just made; the undos run in reverse when the session is disposed (`CleanUpRegistry`) |

`session.Client` is the session as an `HttpClient`. A client generated from a description (Kiota, NSwag) built on it
is guarded, signed, logged and kept as the session's own calls are:

```csharp
var adapter = new HttpClientRequestAdapter(new AnonymousAuthenticationProvider(), httpClient: session.Client);
var client = new ContactsClient(adapter);   // generated by: kiota generate -l CSharp -d api.json -c ContactsClient
```

## Marked resources and the seed

A record a test makes on a shared environment starts its name with the run's marker (`RunMarker.Current`). A kind of
record is declared once, and the session sweeps and deletes by the declaration:

```csharp
static readonly MarkedResource Contacts = new(
    "contact",
    list: session => List(session, "contacts", $"name LIKE \"*{RunMarker.Prefix}*\""),
    read: (session, id) => session.Get($"/contact/{id}") as JsonObject,
    delete: (session, record) => session.Delete($"/contact/{record["id"]}"))
{
    Keep = (session, record) => IsReferredTo(session, record) ? "something refers to it" : null,
};

session.Sweep(Contacts);              // this run's, and what an earlier run left
session.DeleteMarked(Contacts, "42"); // refused when the record's name, as the service gives it, has no marker
```

The rule is in Bruinet, where no suite can forget it: a record is read from the service first, and only one whose
text there carries a marker is deleted. `MarkerField = "*"` takes any text field of the record's own; a resource with
no `delete` is only listed. What `Keep` holds back is in `session.Kept`.

Records tests rely on, with fixed names, are a seed: `ApiSeed.Ensure(session, records)` makes what is not there yet
and leaves what is.

## API objects

An API object is to a subject what a page object is to a screen: the suite's own words for it.

```csharp
public sealed class ContactsApi
{
    internal ContactsApi(ApiSession session) => _session = session;

    public long Create(string name, string type = "Client") { … }
    public JsonObject? Called(string name) { … }
    public bool Delete(long id) => _session.DeleteMarked(Resources.Contacts, id.ToString(CultureInfo.InvariantCulture));
}
```

- Hand-written over JSON when all that is known of the API is what the app was seen to call; a thin layer over a
  generated client when the suite has a description.
- What is the app's own stays here: the body of a create, a list's query, "a delete sends the whole record".
- A scenario says it in the suite's words (`Given a contact "{run} Arend" exists`), bound to an API object. There
  are no generic HTTP steps: a scenario in the API's addresses does not survive a change of the API.
- A test of the suite keeps tests out of the session: Bouw7's `ApiObjectsOnlyTests` fails when a file outside
  `Support/Api` names `ApiSession` or `HttpClient`.

## A form, checked through the API

A test that saves a form proves the screen says it was saved. Reading the record back proves what was stored: a
rounded amount, a date a day off, a field shown and never sent.

```csharp
var write = context.Calls.WriteOf(() => form.Save.Click());            // the call the save made, as the page sent it
var places = FormCheck.Map(typed, write.RequestBody);                   // each typed value's place in the JSON
var stored = api.Contacts.Get(id)?.ToJsonString();                      // the record, read back
var result = FormCheck.Compare("Contact", places, write.RequestBody, stored);
Assert.True(result.Passed, result.ToMarkdown());
```

| Step | With |
| --- | --- |
| The call a save made | `PlaywrightTestContext.Calls` (`PageCalls`): the page's fetch and XHR calls as exchanges. `WriteOf(action)` runs the action and waits for the write it caused; the new record's id is in its answer |
| Which field is which | `FormCheck.Map`: fill each field with a value of its own, and each value is found in the sent body (as text, as a number typed with a comma, as a day typed `21-11-2026`). A field with no place is a finding |
| Typed, sent, stored | `FormCheck.Compare` (`Bruinet.Api.Contracts`): a stored value that differs is a failure, a field never sent a warning. `FormCheck.ToJson` and `FromJson` keep a map beside a page object |
| Reading after writing | Wait for the record by polling the API object (`Settle.Read`), never by a sleep |

Bouw7's `StoredForm.SaveAndCheck(session, form, typed, save)` is these four in one call per form.

## An API's description

`Bruinet.Api.OpenApi` holds a description of an API: its operations and the shape of what each sends and answers.

| A description | Comes from |
| --- | --- |
| Observed | `bruinet api describe --exchanges <file> --out api.json`: merged from the exchanges of a walk, a test run and the API objects' own calls. Shapes only, no values; it says what was seen, never what is promised |
| Described | An OpenAPI 3 document in JSON that someone wrote. YAML and OpenAPI 2 are converted first |

```powershell
$env:BRUINET_API_EXCHANGES = "$PWD\exchanges\run.jsonl"
dotnet test <Suite>                                               # every session's and page's call is kept
bruinet api describe --exchanges exchanges --out <Suite>/api.observed.json --host api-acc.example.com
bruinet api diff <Suite>/api.observed.json                        # against git's HEAD: did the back end change?
bruinet api uncalled --description api.json --exchanges exchanges  # what no test and no walk reaches
bruinet api check --description api.json --exchanges exchanges     # each answer against its schema
```

- **A changed back end** shows in `bruinet api diff` before a test fails: a field gone, a type changed, a status
  added. The `run-triage` skill reads it as "the site changed".
- **A fake back end** for work without the environment: `server.StubDescribed(description)`
  (`Bruinet.Api.Mocking`) stubs every operation with an example of its schema; a stub a test writes wins.
- **Generated calls** (property-based, Schemathesis) are an outside tool a person runs at a gate, with reads only
  (`--include-method GET`), as an account whose `Writes` is `no`, and never against production. Bruinet starts none.

## The api head

A scenario whose Then is about stored data need not go through a screen. Tagged `@api`, it runs on a suite whose
`bdd.config.md` says `Head | api`: the same feature files, bound to API objects, against the running environment,
in well under a second per scenario. It is the `service` head's rule ("ask what the assertion looks at",
[Features below the UI](features-below-the-ui.md)) over the wire instead of in the test process.

- An untagged scenario never runs on `api`; `@api @web` runs on both heads, and binding it on both keeps the two
  vocabularies from drifting.
- A step that opens, drives or reads a screen is a bind error there (BDDB013).
- A spec for a product whose user is another system says `API` in its `Where` row; its rules are about what a
  caller can observe (a status, a field, a message) and its examples are in the API objects' words.

Bouw7's `Bouw7.Api.Tests` is the example.

## Not offered

Generic HTTP steps in scenarios; tests kept as `.http` or Postman files; consumer-driven contracts (a contract is
the DTO the app reads, AD-035); load, performance and security testing.
