## 1. In short

**The idea holds, and more of it is already there than 310 assumed.** The language parses
arbitrary attributes (`label="Name" max=100 message="Name is required"` works today with no
grammar change), has ids, `required`, navigation targets (`@Departments`), bindings, and even a
`validations` table (Field · Rule · Message) in its language specification. It builds, its 371 tests
pass, and its SVG output is deterministic and escapes text.

**But the parser is not yet strict enough to be the source of a spec.** Four defects lose content
without a clear error: an empty table cell shifts the columns, a typo in a closing keyword drops
the rest of the screen, `if`/`else` is lexed but not parsed and loses a branch, and the text of a
`Heading` or `Link` is stored as a placeholder. A spec format must never lose a line silently.
Around the parser, the tools are thinner than the core: the CLI exits 0 on errors and can
overwrite its input, the cache hides errors on a second compile, and the Mermaid plugin and the
VS Code preview put error text into HTML unescaped, which lets a crafted file run script in the
preview. And the project's CI has been red since December 2025.

Verdict: **usable as the basis, after a short hardening pass** (section 6). None of the defects is
deep: the parser's are in 995 readable lines, the tools' are missing escapes, a wrong default
and an exit code. The layout engine is naive (R12), but a spec does not depend on layout.

## 3. What fits a spec profile already

| Need (from 310) | In Wireframe today |
| --- | --- |

| Same input, same SVG | ✅ checked: two compiles are byte-identical; `<` and quotes in labels are escaped |

So a Lirenet profile is mostly **rules on what already parses**: which attributes are allowed on
which kind, that every field has a label, that every `@Target` names a screen that exists.

## 4. Findings: parser and lexer

Each was confirmed by running the input through the built parser. Severity is for use as a spec
source; for drawing wireframes most are minor.

| # | Severity | Where | Defect | Input → result |
| --- | --- | --- | --- | --- |
| W1 | **High** | `parser.ts:760` `parseTableRow` | Empty cells are filtered out, so the cells after an empty one shift left. No error | `\| Name \| \| Name is required \|` → `["Name", "Name is required"]`: the message lands in the Rule column |
| W2 | **High** | `lexer.ts:433`, `parser.ts:386` and peers | An unknown or misspelt closing keyword becomes a block end that no block accepts; every element after it is dropped. The only error is "Expected /wireframe to close document", at the typo's line | `Vertical … /Vertcal`, then `Button "B"` and `Button "C"` → only the `Vertical` remains |
| W3 | **High** | `tokens.ts:279` (lexed) vs `parser.ts` (no case) | `if`, `else`, `/if` are keywords of the lexer, and `ConditionalNode` is in the AST, but the parser never builds one. The `else` branch and everything after is lost | `if loggedIn / Button "Log out" / else / Button "Log in" / /if` → four errors, only "Log out" kept |
| W4 | Medium | `parser.ts:444` | Only nine control types store their string as `text`; for the rest it is `placeholder`. `Heading` and `Link` are not in the list, so a heading's words and a link's words are a "placeholder" | `Heading "Create department"` → `placeholder: "Create department"`, no `text` |
| W5 | Medium | `parser.ts:442` | For a `TextInput`, the only string is the placeholder. There is no label: `Label "Name"` above it is a separate element, not tied to the field | The field's name, which a spec needs most, has no place except a convention or `label=` |
| W6 | Medium | `lexer.ts:765` `isAlpha` | Ids, targets and keywords are ASCII only | `:Categorieën` → "Unexpected character: ë", the id becomes `Categorie` |
| W7 | Medium | `parser.ts` `parseDataSections` | Data sections are only read after all elements and only inside `wireframe … /wireframe`; their header row is not told apart from data rows, and the `component` section's body is never parsed | A `validations` table works only at the end of the file; `componentBody` is always empty |
| W8 | Low | `parser.ts:807` | The "Duplicate ID" error points at the token after the id, not the id | Wrong column in the editor's squiggle |
| W9 | Low | `parser.ts:446` | `Dialog` is in the list of controls with text, but `Dialog` is a component; `ControlType` repeats 15 names that only `ComponentType` produces (`Tabs`, `Table`, `DataGrid`, …) | Dead code and two type lists to keep in step |
| W10 | Low | `lexer.ts:707` vs `:560` | Escapes differ: `\n` in a string is a new line, in a quoted attribute value it is the letter `n` | `message="Line\nTwo"` keeps `n` |
| W11 | Low | `lexer.ts:279` | A `-` or `+` followed by a space starts a tree item anywhere, also in the middle of a line | `Label "Price" - excl. VAT` turns the rest into a list item |

What is good in the parser: small and readable (995 lines), one pass, errors collected with line and
column instead of thrown, ids checked for duplicates, both indentation and explicit closing
keywords accepted.

**Maintainability.** Six `.vsix` builds (about 1.2 MB) and `test-output.*` are committed.
`cli.test.ts` never imports the CLI: it re-implements string operations and even asserts the
opposite of R1, so its tests give false confidence. No tests for the extension, `theme.ts` or
`sketch.ts`. `renderWireframeToHtml` and `escapeHtml` are copied between two extension files;
`extension.ts` (868 lines) and `svg-renderer.ts` (1387 lines) carry too much each. The accessibility
helpers are exported but not used by the renderer.

**For a spec source**: `parse()` is public and returns a typed AST with locations, but there is no
versioned schema, no CLI command that emits it, and no `file:line:col` error format. Output is
deterministic (byte-identical SVG, also for the sketch theme), with long floats such as
`40.44444444444444`.

## 6. What it would take

To be the source of Lirenet's screens, in order:

| # | Change | Size |
| --- | --- | --- |
| 1 | **Green CI**: browser globals for the webview files in the ESLint config | Small |
| 2 | **Never lose content**: keep empty table cells (W1); an unknown closing keyword is an error at its own line, and parsing goes on (W2); `if`/`else` parsed or refused with one clear error (W3) | Small to medium |
| 3 | **Text is text**: `Heading`, `Link` and every control with words store them as `text` (W4) | Small |
| 4 | **A label on a field**: `label="Name"` as a known attribute, or `TextInput "Name"` read as the label in the spec profile, with the placeholder as `placeholder=` (W5) | Small, but a language decision |
| 5 | **Unicode in ids and targets** (W6) | Small |
| 6 | **A strict mode**: unknown attributes, unknown modifiers and unknown `@Targets` are errors, not ignored. The spec profile is strict mode plus a list of allowed attributes per kind | Medium |
| 7 | **A CLI that can gate**: non-zero exit on errors, `file:line:col` messages, never overwrite the input (R1, R6), and `parse --json` so any tool, Lirenet included, gets the tree | Small |
| 7a | **Errors are never hidden or injected**: the cache keeps errors (R5); every error text and label escaped (R2, R3, R9, R10); a CSP and a nonce in the webview; the listener added once (R4) | Small |
| 8 | **Data sections as structured data**: a header row, typed rows, allowed anywhere after the screen; the `validations` table is the field table of [200-Tables.md](200-Tables.md) | Medium |
| 9 | Remove the committed `.vsix` files and `test-output.*` from git | Small |

Items 1–5, 7 and 7a are perhaps three days of work and close every high finding. The CLI's tests
should be rewritten to call the CLI, since today they test a copy of its logic. Item 8 is where
Wireframe and Lirenet's field table become one thing.

**How Lirenet reads it**, given the above: either through `wire parse --json` (Lirenet then needs
Node at check time), or with a C# reader of the profile, tested against the same example files as
the TypeScript parser so the two cannot drift. 310 proposed the C# reader; this review does not
change that, but `parse --json` is worth having anyway and makes a shared test corpus easy.

## 7. Questions

| # | Question | Proposal |
| --- | --- | --- |
| R1 | Fix W1–W3 in Wireframe itself, as general bugs? | Yes: they lose content for every user, not only for specs |
| R2 | `if`/`else`: implement, or remove from the lexer? | Remove for now. A spec states conditions in a rule or a decision table; a wireframe shows one state |
| R3 | The label: `TextInput "Name"` as the label (and `placeholder=` for the hint), or a separate `label=`? | `label=` in the general language, and in the spec profile `TextInput "Name"` *is* the label: one string, the one a person sees |
| R4 | Should the spec profile live in Wireframe (a mode of the parser) or in Lirenet (rules over the tree)? | In Wireframe as `strict` mode with an allowed-attributes list; Lirenet adds only cross-file checks (targets, ids against page objects) |
| R5 | Is the `validations` section the field table, or does the field table stay in Lirenet's Markdown? | Try it as the field table on the department and contact forms; if a person can read it beside the picture, one source wins |
